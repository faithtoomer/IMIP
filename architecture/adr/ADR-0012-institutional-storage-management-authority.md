# ADR-0012: Institutional Storage Management Authority

**Status:** Accepted  
**Date:** 2026-08-08  
**Phase:** 09  
**Deciders:** Architectural Authority (Specification), User (ownership boundary + Law 3 scope)

## Context

The user's initial framing for Phase 09 was a "Storage Authority." Before drafting the specification, the user flagged a real ownership-overlap risk: the Institutional Data Authority (Phase 08) already owns logical data — repositories, persistence, transactions, schemas, migrations, data governance. A "Storage Authority" introduced without a clean boundary would duplicate or blur that ownership. The user resolved this themselves by naming the new authority the **Institutional Storage Management Authority (ISMA)** and drawing the boundary explicitly: IDA owns *data*, ISMA owns *where that data physically lives* (directories, allocation, capacity, retention, archival) — never schemas, transactions, or business entities.

The spec's own Law 3 ("no authority hardcodes filesystem paths — all storage locations originate from ISMA") surfaced a second, real conflict on inspection: IDA's `SqliteStorageProvider` and ICMS's config-file source both already accept a caller-supplied `filePath` directly, with no storage authority involved, because neither existed before this phase. Two implementation paths were possible: (a) build ISMA now and treat IDA/ICMS as a documented, deferred exception to Law 3 (the same posture used for the Capability/Plugin Registry adapters IRBLM still doesn't have), or (b) revise Law 3's application so it actually holds for all three authorities immediately. The user chose (b) explicitly: "with the two already built and conflicted can we revise this law to ensure that they all match?"

## Decisions

1. **ISMA owns physical storage infrastructure; IDA owns logical data — no overlap.** `StorageEntry` (ISMA) never carries a schema, a query interface, or transactional semantics; `DataRecord` (IDA) never carries a filesystem path directly — IDA asks ISMA for one when it wants ISMA-managed storage (see #3).
2. **`allocate()`/`release()`/`resolve()` are synchronous**, using only plain `node:fs` sync calls (`mkdirSync`, `statfsSync`) — no `systeminformation`, which is async. This was a hard constraint, not a preference: IDA's and ICMS's constructors are synchronous by established design (Phases 02/08), and retrofitting them to depend on an async storage call would have been a breaking change to their call model. `discover()` (whole-machine filesystem enumeration via `systeminformation.fsSize()`, matching IHIS's real-hardware-discovery precedent) stays async, since nothing requires it at construction time.
3. **IDA and ICMS are retrofitted with an additive, opt-in `storageAuthority` option** (`DataAuthorityOptions.storageAuthority`, `ConfigurationAuthorityOptions.storageAuthority`), per the user's direction to make Law 3 actually true rather than exempting them. When given, and no explicit `filePath`/`storage` override is supplied, the default storage location is resolved via `storageAuthority.allocate(...)` instead of IDA's previous `:memory:` default or ICMS's previous "no config file" default. Omitting `storageAuthority` preserves each authority's exact pre-Phase-09 behavior — this is non-breaking for all 383 pre-existing tests across both modules, which continue to pass unmodified. An explicit `filePath`/`storage` always wins over `storageAuthority`, so an operator can still pin an exact location when needed.
4. **ISMA mirrors onto the IEB (ADR-0009 §6 pattern), rather than publishing directly like IRBLM (ADR-0010).** IRBLM's public API was already fully async, so it could publish and await in the same call. ISMA's public API must stay synchronous (decision #2), so it cannot await a publish — it fires events onto its own local `EventEmitter` synchronously and mirrors onto the IEB fire-and-forget, `.catch()`-swallowed, exactly like `ConfigEventBus`/`HardwareEventBus`.
5. **A new `'storage'` `EventCategory` was added to the Event Bus** (`core/event_bus/src/types.ts`), additive and non-breaking (a union-widening, no runtime validation array to update). The existing `'database'` category was considered and rejected for ISMA's events: reusing it would blur exactly the IDA/ISMA line decision #1 draws, since `'database'` reads as "logical database operations," not "physical storage infrastructure." `'database'` remains unused by any concrete registered event today — IDA does not publish to the IEB.
6. **Capacity measurement uses two complementary real sources, not one.** `fs.statfsSync` (Node's built-in, synchronous, no new dependency) powers per-entry health checks; `systeminformation.fsSize()` (already a platform dependency via IHIS) powers the broader, async, whole-machine `discover()` scan. Neither is a placeholder — both return real OS-reported numbers.
7. **`release()` deregisters an entry without deleting its underlying files.** Physical deletion is a distinct, explicit operation (`enforceRetention()` for policy-driven cleanup, `archive()` for a checksummed copy-then-mark-archived flow) — an authority calling `release()` to stop using a location should not risk silently losing data it didn't intend to delete.

## Consequences

- Constructing `new DataAuthority({ storageAuthority: isma })` or `new ConfigurationAuthority({ storageAuthority: isma })` now gives each authority a real, ISMA-managed default file location instead of an in-memory or file-less default — but only when the caller opts in, so every existing call site and test is unaffected.
- Every future authority that needs durable storage follows the same pattern: accept an optional `storageAuthority`, allocate a path in the appropriate domain, never hardcode a path.
- ISMA's Institutional Storage Topology (§22) becomes the platform's standing answer to "where does everything live and how healthy is it," independent of which authority allocated what.
- The Event Bus's category list is no longer purely a Program I artifact — Program II authorities are expected to add new categories as needed, following the same additive-widening pattern used here.
