# ADR-0019: Institutional Power Intelligence Authority

**Status:** Accepted
**Date:** 2026-08-08
**Phase:** 16 (Program III, first phase)
**Deciders:** Architectural Authority (Specification), User (naming/scope framing)

## Context

The user opened Program III — Resource Intelligence — by reframing power from a static setting into a managed institutional resource, naming Phase 16 the Institutional Power Intelligence Authority (IPIA): not a wattage controller, but the platform's authority for power monitoring, cost, efficiency, budgeting, and explainable, advisory-only recommendation.

Per the user's now-standing instruction, the spec was checked against every authority already touching power, energy pricing, or event/log/notification categories before any code was written. This review turned up more already-real groundwork than any prior phase:

1. **IHIS (Phase 03) already tracks real GPU power data.** `GpuInfo.powerLimitWatts`/`RawGpuInfo.powerLimitWatts` are populated from `systeminformation`'s real `si.graphics().controllers[].powerLimit` (`discovery.ts:134`). `HardwareCapability` already includes a real `'power-monitoring'` flag, assigned whenever a device reports a rated power limit (`assessment.ts:40`). IHIS's own `digitalTwin.ts` already computes a `performancePerWatt` efficiency estimate from `bestBenchmark.value / powerLimitWatts`, embedded in `EfficiencyProfile` as one input to Digital Twin suitability scoring.
2. **`systeminformation` (already a dependency, used by IHIS and ISMA) also exposes real, live `powerDraw`** on the same `GraphicsControllerData` type IHIS already reads — currently uncaptured by IHIS's discovery pipeline, since discovery is a point-in-time inventory snapshot, not continuous sampling.
3. **`'power'` is already a reserved `EventCategory`** (part of the Phase 01 original 19-value union), already listed in INCA's notification categories and IOLA's observability categories — with zero current producers anywhere in the platform. This is the first phase in this engagement that needs no additive category widening anywhere.
4. **ICMS (Phase 02) already has a complete `'electricity'` config category** — `electricity.rate`, `electricity.currency`, `electricity.billingModel` (`flat`/`time-of-use`), `electricity.timeOfUseSchedule`, `electricity.peakPricing`, `electricity.offPeakPricing` — fully defined in `registry.ts` since Phase 02, with zero current consumers.
5. **No real revenue, share, or mining-session tracking exists anywhere.** IDA's `DataDomain` union already reserves `'mining-sessions'` and `'profitability-history'` as honest, zero-producer extension points; no authority populates them yet.
6. **No `DataDomain` value cleanly fits power history.** The existing `'telemetry'` value is real but ambiguous — already loosely touched by ISMA's own storage-domain naming and ICMS's own `'telemetry'` config category, and used in tests only as an arbitrary placeholder string, never actually claimed by a real authority.

## Decisions

1. **IHIS is not modified.** Its `performancePerWatt` is a narrow, rated-power-based input to Digital Twin *suitability scoring* — a different purpose (which device is a good fit for a workload) from IPIA's institutional power *governance* (monitoring, cost, budgets, explainable recommendations). Changing an already-certified Program I module to serve a Program III authority would invert the platform's dependency direction; IPIA depends on IHIS, never the reverse — the same resolution already used for the "Access Authorization" vs. "Decision Pipeline Authorization" naming overlap in ADR-0015. IPIA becomes the platform's authoritative source for anything genuinely called power intelligence (cost, budgets, measurement-based efficiency, recommendations); IHIS's estimate stays exactly as it is, serving exactly its original narrow purpose.
2. **IPIA's own Telemetry Collector owns live sampling; IHIS keeps owning static discovery.** The two are genuinely different concerns — a one-time (or per-rescan) inventory snapshot versus continuous power draw sampling — mirroring the same "physical storage vs. logical data" split already established between ISMA and IDA (ADR-0012). For GPUs, IPIA reads `systeminformation`'s real `powerDraw` directly; IPIA never re-implements IHIS's discovery pipeline, and reads rated power limits (`maximumRatedPowerWatts`) and the `'power-monitoring'` capability flag straight from IHIS's real, already-certified registry rather than re-discovering them.
3. **No electricity-pricing config was added — it already existed.** `computeCost()` reads ICMS's real `electricity.rate`/`electricity.billingModel`/`electricity.timeOfUseSchedule`/`electricity.peakPricing`/`electricity.offPeakPricing` directly; IPIA is simply the first real consumer of a config surface Phase 02 built two Programs ago.
4. **`DataDomain` gains one new, precise value: `'power-history'`**, rather than overloading the ambiguous existing `'telemetry'` value — the same additive-widening precedent as `EventCategory`'s `'storage'`/`'resilience'`/`'version-governance'` (ADR-0012/0017/0018), reserving `'telemetry'` for whatever future authority is actually meant to own it broadly.
5. **One small, precise additive retrofit to ICMS: `hardware.estimatedPsuEfficiency`.** §7's "estimated wall power" needs a real, explainable overhead factor to derive platform-level draw from summed component draw — rather than a hardcoded constant (which this codebase's own conventions treat as a real defect everywhere else), it is a real, configurable, documented ICMS value (category `hardware`, default `0.9`, range `[0, 1]`), so the derivation is fully explainable and operator-tunable, not a magic number.
6. **Revenue-based efficiency metrics (`revenuePerKwh`, `costPerAcceptedShare`) are honest, undefined-by-default fields behind an injectable `RevenueSource`.** No real revenue or share data exists anywhere in this codebase yet — fabricating either would violate Law 3 ("Measurement Before Optimization") more than reporting them as genuinely unavailable. `hashesPerWatt`, by contrast, is real today: IPIA's own measured wattage divided by IHIS's real, already-certified best-benchmark hash rate.
7. **CPU and ASIC live power telemetry are real, honest, zero-producer extension points**, via an injectable `PowerSensorProvider` per `HardwareCategory` — `systeminformation` has no cross-platform CPU package-power or ASIC power reading today, so IPIA reports `PowerSensorUnavailable` rather than fabricating a value for these categories, exactly the same shape as every other "real extension point, zero registrations yet" pattern in this platform (ASIC discovery in IHIS, Email channel in INCA, Plugin/Capability Registry in IBRRA/IVGMA).
8. **`HardwareAuthority` and `ConfigurationAuthority` are required constructor dependencies, not optional ones.** Every prior Program II/III cross-cutting authority (IOLA, IBRRA, IVGMA) treats its EventBus/ObservabilityAuthority/DataAuthority integrations as optional, since those authorities can do *something* meaningful standalone. IPIA cannot: without real device identity/capability/benchmark data and real electricity pricing, there is nothing genuinely measurable to report — Law 3 makes both dependencies load-bearing, not decorative. `eventBus`, `observabilityAuthority`, and `dataAuthority` remain optional, matching the established pattern.
9. **Power modifications are structurally impossible, not merely disallowed by convention.** IPIA's public interface (§16) exposes only lookups and advisory recommendation generation — there is no method anywhere in the module's surface that writes to a hardware power limit, satisfying Law 6 and the Cursor contract's explicit prohibition by construction rather than by discipline alone.
10. **§13's literal linear lifecycle (`Discovered → Profiled → Monitored → Analyzed → Optimized → Archived`) is extended with real cycle-back and any-stage-archival edges**, since a continuously operating monitoring authority cannot honestly be one-shot: `monitored ⇄ analyzed ⇄ optimized` all remain reachable from each other, and `archived` is reachable from `monitored`, `analyzed`, or `optimized` (a device can be removed from the fleet — IHIS reporting it gone — at any point, not only after a full linear pass). The same kind of honest, documented extension already made to `VersionStatus`/`MigrationStatus` in ADR-0018.

## Consequences

- Phase 16 needs the smallest additive footprint of any phase in this engagement: one new `DataDomain` value and one new `ConfigCategory` entry (`hardware.estimatedPsuEfficiency`) — no new `EventCategory`, no new notification/observability category, no ICMS electricity-pricing work at all.
- IHIS, ICMS, and the Event Bus's `'power'` category all remain exactly as they were before this phase except for the two additive entries above — Program I and Program II stay untouched in every other respect.
- Program III begins with the same governing discipline as Program II: real cross-authority orchestration over reimplementation, fail-honest reporting over fabricated data, and advisory-only output where hardware safety (Law 6) is at stake.
